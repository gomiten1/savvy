Status: `settled` | `assumed` (implicit, not yet challenged) | `open`.

| D12 | We design **agnostic to the teammate's database** — our side talks to an interface, not a concrete store | settled | 2026-08-29 | Contract shape TBD |
| D13 | Detector scans **1-D and 2-D slices only**, with `provider` and `issuing_bank` always in the scan set — and always as *pairs* too (`provider×country`, `issuing_bank×merchant`), since the challenge scenarios live there. No 3-D+ scan | settled | 2026-08-29 | Provider/bank chosen for operational significance + enough volume to be detectable without country-level dilution |
| D14 | Detector emits **signals**, not alerts. A deterministic **clusterer** groups co-moving signals into candidate **incidents**. The agent receives a cluster | settled | 2026-08-29 | Gives "two simultaneous incidents separated" deterministically instead of hoping the LLM does it |
| D15 | Detector **polls** windowed aggregates (~10s cadence); it does not consume an event stream | settled | 2026-08-29 | Detection latency is bounded by statistical confidence (60-180s of data), not by transport. Streaming would buy ~10s against a ~120s floor |
| D16 | The agent **queries** the store for drill-down; only the detector is on the polling path | settled | 2026-08-29 | |
| D17 | Canonical metric: `conversion = approved_attempts / total_attempts` (**attempt-level**). Money cost estimated at **payment-level** (a retry that eventually succeeded cost latency, not revenue) | settled | 2026-08-29 | |
| D18 | Mock stream generator, injection UI, and the gold/medallion pipeline are owned by **Maca and Malu**. We own detection, clustering, diagnosis, memory, Slack | settled | 2026-08-29 | Interface pinned in docs/DATA-CONTRACT.md |
| D19 | **Slack is the UI.** Terminal for stream/detector logs. No web frontend built by us | settled | 2026-08-29 | 18h budget |
| D20 | Generator runs on **accelerated simulated time**; "reasonable detection time" is measured in simulated minutes | settled | 2026-08-29 | Demo must fit ~2 min inside a 10 min pitch |
| D21 | Cells below a **minimum attempt volume** per window are not evaluated and are reported as *insufficient evidence*, never fired on | settled | 2026-08-29 | Doubles as the bonus-point "admits the evidence isn't enough" path |
| D22 | Incident lifecycle / alert dedup is **our scope**, not the pipeline's. Medallion gold dedups transactions, not incidents | settled | 2026-08-29 | Corrected a misattribution |
| D23 | Scan **all 1-D and all 2-D slices** (6 + 15 pairs). No hand-picked dimension pairs. The volume gate prunes low-traffic combos automatically | settled | 2026-08-29 | Reverses D13's hand-picking. Removes an arbitrary choice and removes a trial-by-fire blind spot if judges inject on an unpicked pair. Cost: ~300 simultaneous hypothesis tests -> handled by calibration (D24) |
| D24 | Detection thresholds (p-value, minimum absolute drop, minimum attempts) are **calibrated empirically by replaying the clean backfill** until the detector fires zero times — they are not chosen a priori | settled | 2026-08-29 | 5pp / n>=50 / p<1e-4 are placeholders only. Calibration is also the answer to multiple-comparisons across ~300 cells, and is the pitch line: "two weeks of normal traffic, zero alerts" |
| D25 | Clustering: greedy anchor + lattice containment. `lost_approvals = attempts x (p0 - p_obs)`; highest is the anchor; absorb firing cells whose filter dict is a subset/superset of the anchor's; repeat on the remainder for the next incident | settled | 2026-08-29 | Deterministic separation of simultaneous incidents, no LLM involved |
| D26 | Incident identity = the **first** anchor cell's signature; `current_anchor` tracked separately because the anchor drifts as an incident matures | settled | 2026-08-29 | Without this, one incident splits into two Slack root messages mid-demo |
| D27 | Incident state (`OPEN`/`RESOLVED`, debounce counter, miss streak) is an **in-memory registry we own**, persisted to the memory store on close | settled | 2026-08-29 | |
| D28 | Open requires firing on **2 consecutive evaluations**; resolve after **K consecutive non-firing evaluations**. Resolution inherently lags by the window length as the sliding window drains | settled | 2026-08-29 | |
| D29 | **Two-phase Slack alert**: code posts the deterministic root message immediately on open (cell, since-when, magnitude, burn rate); the agent posts its diagnosis into that **thread** when done | settled | 2026-08-29 | Perceived latency = detection latency; alert stays useful if the LLM fails or times out (trial-by-fire insurance); two visible demo beats |
| D30 | Agent budget: **90s or 15 tool calls**, whichever first, then forced to answer with what it has | settled | 2026-08-29 | Raised from 45s/10 because phase-1 already absorbed the perceived latency |
| D31 | Agent tools: `get_counts`, `get_samples`, `search_memory`, `get_baseline`. Agent returns **structured JSON**; Slack formatting is done by our code, never by the LLM | settled | 2026-08-29 | Stops an unlabelled hallucinated number reaching the channel |
| D32 | Agent is instructed to state confidence and to explicitly report **insufficient evidence + what it would need**, rather than guessing | settled | 2026-08-29 | Bonus-point scenario |
| D33 | Money is reported as a **burn rate** (`lost_approvals_per_hour x avg_amount_usd x (1 - retry_recovery_rate)`), isolated in a single module with constants at the top so it can be changed in one place | settled | 2026-08-29 | Burn rate does not require the incident to be over; "money lost by the minute" is the challenge's own framing |
| D34 | `decline_code` is **removed as a scan dimension**. Approved attempts have a null decline code, so conversion rate grouped by it is meaningless. It becomes a **characterization attribute** the agent inspects on an already-firing cell | settled | 2026-08-29 | Corrects D23/the original 6-dimension framing. Scan dimensions are now 5 -> 10 pairs, not 15 |
| D35 | Scan set = **core (always) + opportunistic (budget permitting)**. Core, from payment-analytics practice (Yuno): `issuing_bank`, `provider`, `provider x country`, `issuing_bank x country`, `issuing_bank x method`, `method x country`, `merchant x provider`. Remaining 1-D/2-D cells scanned when volume and compute allow | settled | 2026-08-29 | Yuno ranks issuer as the highest-priority lens, then BIN, market, method, decline reason; names issuer x method and market x method explicitly. Their worked example ("approval drop in Brazil, issuer timeouts on one acquirer") is our scenario 2 |
| D36 | We **never enumerate the cube**. Cells come from `GROUP BY` on live data, so only non-empty cells exist; the volume gate then bounds testable cells by `throughput / min_attempts` - linear in traffic, independent of dimension cardinality | settled | 2026-08-29 | This is the scalability answer. Hand-picking pairs is a priority prior, not a scaling mechanism |
| D37 | Ranking metric is **lost approvals**, matching Yuno's "rank markets, issuers, and payment methods by lost approvals" | settled | 2026-08-29 | |
| D38 | **Config vs state split.** Repo (versioned): playbook.md, dimension/context catalogue (md + csv), threshold config. Gitignored (state): `incidents.db`, baseline artifacts. Only state can diverge from the repo - config *should* be versioned | settled | 2026-08-29 | Resolves the original repo-divergence worry: it only applied to state |
| D39 | Incident registry is an in-memory dict **write-through** to `incidents.db` on open and on close. Process restart loses in-flight incidents; acceptable for MVP | settled | 2026-08-29 | |
| D40 | Baselines are an **immutable versioned artifact**. Recompute writes a new file and atomically swaps a pointer; the previous version is retained for rollback. **Zero downtime** - a read-only artifact swap never needs any | settled | 2026-08-29 | Corrects the assumption that a model swap costs seconds of downtime |
| D41 | Recompute **nightly** over a trailing 4-week window, excluding windows belonging to known Incidents. For the 18h build: compute once from the backfill at startup, ship the exclusion clause, skip the scheduler | settled | 2026-08-29 | Weekly is too slow for hour-of-week baselines to track routing/merchant-mix changes; nightly costs nothing given zero-downtime swap |
| D42 | Agent budget set to **120s / 15 tool calls**. Chosen by judgement, **not yet justified** - test T5 in docs/TESTING.md exists to calibrate it | assumed | 2026-08-29 | Explicitly marked assumed so it gets tuned rather than defended |
| D43 | Incident priority = **burn rate** primary, **blast radius** as tiebreaker and display label. Ranking is computed by our code; the agent sees one incident at a time and never sees the ordering | settled | 2026-08-29 | Prevents a small total outage being buried under a large partial one |
| D44 | Memory retrieval is **deterministic SQL over lattice-related cells**, ranked by recency - not semantic search. The LLM judges whether it is truly the same story; SQL decides what it may see | settled | 2026-08-29 | Semantic search over a handful of rows is theatre and invites false "this happened Tuesday" claims |
| D45 | Slack: **one channel**. Root message = deterministic facts + bold exec one-liner. Thread = agent's ops detail, evidence, recommended action, confidence, and the resolution note | settled | 2026-08-29 | Delivers the two-audience bonus structurally |
| D46 | Diagnosis reports go to a **second, separate store** (`reports.db`), append-only and revisioned per `(incident_id, revision)`, consumed by the dashboard. Contract in `docs/DASHBOARD-CONTRACT.md` | settled | 2026-08-29 | `incidents.db` is operational hot-path state (small, latency-sensitive, written in the detector loop); this is a read-heavy analytical sink with a different consumer and different failure tolerance |
| D47 | The reporting pipeline is **strictly downstream of alerting and non-blocking**. It may be slow, may retry, and its failure must not affect Slack alerts. Idempotent per `(incident_id, revision)` | settled | 2026-08-29 | This is what makes "recording here can be slow" acceptable |
| D48 | The reporting step **copies** deterministic figures from the main path (`onset_ts`, `burn_rate_usd_hour`, `blast_radius`, `affected_entities`) and **never recomputes them**. It may only rewrite prose | settled | 2026-08-29 | If a secondary agent re-derives money or onset, the dashboard and the Slack message disagree in front of judges |
| D49 | A new report revision is published on: first diagnosis (rev 1), a material change that re-runs the agent, and incident resolution. Dashboard live view = latest revision per incident; audit view = full history | settled | 2026-08-29 | |
| D50 | Whether the reporting step is a **secondary agent or plain code** is deliberately left open — it does not block the dashboard team, who build against the seeded schema | open | 2026-08-29 | |
| D51 | Dashboard team unblocks immediately by building against a **seeded `reports.db`** (open / resolved / insufficient_evidence / repeat, plus one two-revision incident) — same pattern as the detector building against a fake `get_counts` | settled | 2026-08-29 | |
| D52 | **Onset is backdated deterministically.** On open, walk the anchor cell's per-bucket rates backwards until the first bucket not below baseline; the next bucket is `onset_ts`. Slack reports onset and detection time separately ("started 14:03, detected 14:06") | settled | 2026-08-29 | The challenge scores "since when". Showing the gap honestly is stronger than hiding it - it is the number we are meant to be minimising |
| D53 | **Cold-start baseline fallback, three tiers:** (1) `(cell, hour_of_week)` if it has >=K observations, else (2) `(cell, all_time)`, else (3) the **parent cell's** baseline. If even the parent is unknown, the cell is marked `no_baseline` and routed to the insufficient-evidence path, never silently dropped. The tier used is attached to the signal and surfaced as evidence | settled | 2026-08-29 | Closes a live trial-by-fire blind spot (judges inject on a cell with no history). Surfaced to the dashboard as `baseline_source` (D46) |
| D54 | A **context catalogue** (repo-versioned csv/md) complements the playbook: per provider - countries/methods served, gateway vs acquirer; per method - card-based (so `issuing_bank` is meaningful) vs push/APM like Pix or SPEI; per country - local method mix | settled | 2026-08-29 | Prevents the agent generating domain nonsense such as "issuing bank B7 is declining Pix" |
| D55 | The `throughput / min_attempts` scalability bound is **accepted but not yet understood** by the team. Logged in docs/TO-STUDY.md to be verified before it is defended to judges | open | 2026-08-29 | Honesty flag, not a blocker |
| D56 | **One detector, two narratives.** Conversion counts both `declined` and `error` as failures (single money-relevant metric, one alerting system). But `error_share` and the decline-code mix are attached to every signal as characterization, and the playbook branches on them: elevated `error_share` => provider/infrastructure story; normal `error_share` with a shifted decline mix => issuer/risk story | settled | 2026-08-29 | Yuno's worked example ("elevated issuer timeouts on one acquirer") is an error-rate story, not a decline story. Two detectors would double the alerting surface for no gain |
| D57 | The test is **one-sided**: only drops below baseline fire. Conversion improving is never an incident | settled | 2026-08-29 | |
| D58 | Recommended actions come from a **finite action library** in the context catalogue. The agent *selects and parameterizes* an entry, never invents one, and may return `no_safe_action` with reasoning. Each entry states a precondition, so our code can reject a recommendation that contradicts the catalogue (e.g. rerouting to a provider that does not serve that country) before it reaches Slack | settled | 2026-08-29 | Stops plausible-sounding nonsense; makes the recommendation machine-checkable |
| D59 | Action library entries carry an **owner and an addressable next step** - a named operator contact and, where applicable, a drafted message body. Example: "email Juan Tellez (ops, Mercado Pago) with: <drafted email>". Contacts are fictional, consistent with the fictional PagoTotal scenario | settled | 2026-08-29 | Sebastian's point: this makes the output consumable by a downstream actuator - a future agent could send the email or fire the action automatically. We deliberately stop at recommending (D11), but we emit something that is *shaped* to be executed |
| D60 | Context catalogue therefore includes an **ownership table**: per provider -> ops contact; per merchant -> account manager; per bank/acquirer -> relationship contact | settled | 2026-08-29 | Required by D59 |
| D61 | Demo is **four beats in ~2 minutes**: (1) ~20s stream at 20x, Slack silent, terminal showing cells evaluated / 0 signals; (2) ~30s injection -> root Slack message with cell, onset, burn rate, exec one-liner; (3) ~40s thread fills with diagnosis + evidence + recommended action, second incident opens as its own root message ranked below; (4) ~30s judge drives the injector. **A screenshot of a successful run is kept as a fallback slide** | settled | 2026-08-29 | If the API hangs at 20x in front of judges, narrate the screenshot and keep moving rather than debugging on stage |
| D62 | Build order: (1) fake `get_counts` + backfill loader ~1h; (2) baselines + detector + T1 calibration ~3h; (3) clusterer + lifecycle + Slack root message ~3h **<- fully demoable with no LLM**; (4) agent + playbook + tools ~4h; (5) memory + T7 ~1.5h; (6) trial-by-fire rehearsal ~2h; ~3.5h slack. **Cut line at hour 12: drop memory and the resolution message. Never drop two-incident separation or the rehearsal** - both are explicitly scored. Rehearsal must be driven by someone who did not choose the injection | settled | 2026-08-29 | Step 3 being demoable without the LLM makes the agent additive rather than load-bearing |
| D63 | **Confidence is a three-level enum** (`high`/`medium`/`low`), never a fabricated percentage - an LLM-produced "87% confident" has no referent and dies to the question "87% of what?". Low confidence carries an internal `low_confidence_reason`: `no_baseline`, `below_volume_gate` (both deterministic and demoable on command) or `competing_explanations` (agent found >=2 cells each explaining a large share, neither dominant) | settled | 2026-08-29 | The insufficient-evidence bonus scenario has to be reproducible on purpose, so its deterministic causes are separated from the agent's judgement |
| D64 | **`budget_exhausted` is internal telemetry only and is never surfaced to the user.** When the agent hits its cap without isolating, the output reports an *inconclusive investigation*: what was checked, what was ruled out, and what remains open for deeper research. It never blames its own budget | settled | 2026-08-29 | Sebastian: the operator needs the state of the investigation, not the machine's excuse. Also strictly better on stage - it reads as rigour rather than failure |
| D65 | **Last-mile storm cap.** If more than 3 incidents are open simultaneously, post the top 3 by burn rate individually and collapse the remainder into one "N further incidents open" summary with a table. Only the top 3 get an agent run; the rest get deterministic root messages only | settled | 2026-08-29 | Per-incident dedup does not protect against many simultaneous incidents - the "fires on everything" failure arriving through the unguarded door. Also caps latency and API spend if a judge injects something very broad |
| D66 | **Material change** (re-runs the agent, posts to thread) = burn rate doubles versus the value at last diagnosis, OR the anchor cell changes lattice branch (not mere drift within one) - AND at least 5 minutes of sim-time since the last agent run. Hard cap of 3 agent runs per incident | settled | 2026-08-29 | Tightens D29. Without cooldown and cap, a slowly worsening incident re-runs every tick and buries its own root message |
| D67 | **One Python process, threads**: a detector loop thread, an agent worker thread (so a 120s LLM call never stalls detection), a `queue.Queue` between them. No broker, no docker-compose. The generator is a separate process owned by Maca/Malu | settled | 2026-08-29 | 18h budget. We describe it honestly as threads-and-a-queue; the production shape we would build instead is written up in docs/TO-STUDY.md so it can be explained on demand |
| D68 | **Settled: the principle.** Each cell is compared to its *own* historical behaviour, with the baseline split into a **level** (`cell x hour_of_week`) and a **dispersion** (residual scale, pooled across windows for the cell). This is a light seasonal linear model / descriptive-stats approach, not a coin-flip assumption. **Deliberately deferred: the estimator.** Whether dispersion is std, MAD, an empirical quantile or beta-binomial is chosen from the EDA (T0) on the real backfill, not a priori | settled (principle) / open (estimator) | 2026-08-29 | Motivated by overdispersion: real approval rates wobble more than binomial variance allows (customer mix, BIN mix, amounts), so a naive `binomtest` on a high-volume cell over-fires and lets the pp gate do all the real work. Same discipline as D24 - the data picks the numbers |
